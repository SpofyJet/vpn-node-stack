# Изменения

## 1.4.7 — установщик 1.4.7, node 1.2.4, shieldnode 1.2.4 (2026-09-28)

**Блок-листы больше не остаются пустыми часами.** Прод (3 ноды) и лаба:
- **После перезагрузки все списки пусты до ~6 ч.** Updater брал основной lock без ожидания; ports-watch
  держит его доли секунды каждые 15 с, и тик, попавший в этот миг, пропускался целиком — следующий через
  интервал (360 мин). Лаба: таймер сработал через 5 мин после boot — «main lock занят — пропуск тика»,
  следующий запуск через 5 ч 55 мин. Теперь updater ждёт lock до 120 с.
- **Прерванное / неудачное первое обновление** (перезагрузка посреди загрузки, фид не ответил) больше не
  ждёт общего таймера: новый `shieldnode-blocklist-retry.timer` каждые 10 мин (и через 6 мин после boot и
  apply) заполняет пустые наборы — из снимка на диске, иначе из сети. Заполненные наборы и пустые «по
  праву» (успешное пустое обновление) не трогает; после 3 неудач подряд — не чаще раза в час.
- **raw.githubusercontent.com недоступен** у части хостеров (прод: таймаут — scanner неполный, свой список
  не обновлялся): при сбое загрузки с GitHub updater берёт тот же файл через jsDelivr
  (`cdn.jsdelivr.net/gh/<владелец>/<репо>@<ветка>/<путь>`).
- **CrowdSec не установлен** (пакет не поставился при apply; agent-режим): раньше каждые 30 мин служба
  падала, счётчик сбоев рос, health — три WARN «set ПУСТ / фид падает подряд / нет last-good». Теперь
  это не сбой фида: одно WARN «crowdsec не установлен (cscli нет)» с подсказкой (повторить apply или
  `ENABLE_CROWDSEC_LIST=0`), запись в лог — раз в сутки.

## 1.4.6 — установщик 1.4.6, node 1.2.4, shieldnode 1.2.3 (2026-09-27)

**`reality-check` правильно проверяет selfsteal-dest.** Раньше `dest` вида `127.0.0.1:8443` проверялся
без SNI (fakesite на Caddy отвечает только на свой домен — проверка писала «недоступен»), а путь к
unix-сокету превращался в «/dev/shm/…:443». Теперь проверка идёт так же, как ходит REALITY: к адресу
`dest` (TCP или unix-сокет, в т.ч. `@абстрактный`) с SNI из `serverNames`; selfsteal помечается в отчёте.
Замеров 5 вместо 3 (на шумной VM один выброс давал 54 мс вместо реальных 6–13).

Замер на тестовой ноде (VLESS+REALITY, время до первого байта, медианы): `dest` = `www.cloudflare.com`
(~4 мс от ноды) — 38–41 мс; selfsteal на этой же ноде (`127.0.0.1:8443`) — 17–20 мс; через unix-сокет —
15–17 мс, то есть так же, как `127.0.0.1`, в пределах шума.

## 1.4.5 — установщик 1.4.5, node 1.2.3, shieldnode 1.2.3 (2026-09-27)

**UDP / Hysteria2: разбор на тестовой ноде (Hysteria2 в rw-core, Xray 26.7.28, нагрузка iperf3).**
Дополнительная настройка UDP-буферов и памяти **не нужна**:
- quic-go просит у ядра ровно 8 МиБ на сокет и получает их (в учёте ядра 16 МиБ) даже при значениях ядра
  по умолчанию — у контейнера remnanode есть `NET_ADMIN`; `rmem_max` 8 МиБ node страхует контейнеры без
  него. Больше quic-go не просит — поднимать `rmem_max` выше бесполезно;
- при 100% CPU в 8 потоков очередь сокета — максимум 5,3% буфера, память UDP ядра — 1 МБ из 233 МБ до
  порога давления; потерь сокета, `RcvbufErrors`, softnet — 0;
- UDP-лимит shieldnode на IP не трогает сессии Hysteria2: после ответа сервера они `established` и
  принимаются раньше лимита (все 194 084 пакета нагрузки — established). Прежнее обоснование лимита
  («ядро склеивает QUIC-пакеты, GRO») было неверным: quic-go не включает `UDP_GRO`, фаервол видит каждый
  пакет — исправлено, добавлен тест.
- `node status` показывает для UDP-сокетов Xray реальный буфер и потери, память UDP, `RcvbufErrors` и
  RX-кольцо карты — с подсказкой причины потерь (мал буфер -> `rmem_max`/`NET_ADMIN`; буфер полный -> CPU).

**Меньше фоновой нагрузки: служба слежения за портами shieldnode — 67 -> 19 мс CPU на проверку.** На
тестовой ноде (1 vCPU) она постоянно ела 0,45% ядра: каждые 15 с `pgrep` обходил все процессы. Теперь
один `ss` через netlink (только слушающие сокеты); перезапуск Xray виден по новому имени его API-сокета.

**`tools/audit-node-perf.sh`** — аудит производительности ноды, только чтение (~1,5 мин): CPU и steal,
фоновые службы (CPU/запись на диск), рост логов Xray, сетевая карта (очереди, кольцо, offload,
прерывания, softnet по CPU), TCP/UDP, conntrack, скорость DNS без кэша, синхронизация времени, всё ли
применено после перезагрузки. IP в выводе маскируются.

## 1.4.4 — установщик 1.4.4, node 1.2.2, shieldnode 1.2.2 (2026-09-27)

**Быстрее первая загрузка через VPN: начальное окно TCP 32 вместо 10.** VLESS без mux открывает к ноде
отдельное TCP-соединение на каждое соединение приложения, и каждое начинается с окна ядра в 10 пакетов
(~14 КБ). Ответ сайта приходит клиенту за несколько лишних кругов «туда-обратно». Теперь на маршрутах
по умолчанию ноды стоит `initcwnd 32 initrwnd 32`.

Замер на тестовой ноде (загрузка объекта через VLESS+REALITY, новое соединение на каждый запрос, медианы):

| Канал клиента | 16 КБ | 64 КБ | 256 КБ | 1 МБ |
|---|---|---|---|---|
| RTT 60 мс | −21% | −20% | −19% | −15% |
| RTT 120 мс, 1% потерь | −22% | −20% | −15% | −13% |
| 4 Мбит/с, мелкий буфер, RTT 100 мс | −16% | −17% | −2% | −4% |

Окно 64 быстрее на хороших каналах (до −36%), но на медленном канале с мелким буфером на 8% медленнее
окна ядра — поэтому по умолчанию 32, а 64 — по желанию: `TCP_INITCWND=64` в `/etc/node/node.conf`
(`0` — окно ядра).

- Настройка живёт в трёх местах: сразу (`ip route change`), после перезагрузки (`node-rt-tweaks`), при
  продлении DHCP-аренды (drop-in networkd `[DHCPv4] InitialCongestionWindow=`). Откат снимает всё.
- Если networkd продлит аренду до перезагрузки, он добавит второй маршрут по умолчанию без окна; ядро
  продолжает использовать наш (первый) — проверено по `cwnd` нового соединения.
- `node status` показывает план и фактическое окно.

**Проверка скорости dest у REALITY** (`node reality-check`, в меню: Оптимизация → 6). На каждое подключение
клиента REALITY открывает соединение к `dest` и ждёт его TLS-ответ. Лаба: `dest` дальше на 150 мс →
время до первого байта у каждого нового соединения 23 → 322 мс. Проверка измеряет с ноды рукопожатие
TCP+TLS 1.3 до текущего `dest` (берётся из работающего Xray, приватный ключ и пользователи не выводятся
и не пишутся) и до вариантов, проверяет TLS 1.3 и HTTP/2 и подсказывает более быстрый. `dest` меняется
в панели — конфиг Xray стек по-прежнему не трогает.

**Меню после обновления перезапускается новой версией установщика** — раньше шапка показывала старую
версию установщика до выхода из меню.

## 1.4.3 — установщик 1.4.3, node 1.2.1, shieldnode 1.2.2 (2026-09-27)

**Клиентов больше не ограничивают ни на мобильном интернете, ни на Wi-Fi: лимиты на IP возвращены
к значениям и поведению старого shield 4.1.0.** Превышение лимита больше никогда не банит IP целиком,
отбрасываются только лишние пакеты. За мобильным CGNAT или общим Wi-Fi на одном IP много людей, и бан
одного выключал всех. На боевой ноде так были забанены 2 IP: 71 292 отброшенных пакета их повторов.

| на один IP, защищаемые порты | 1.2.0 | 1.2.1 | **1.2.2** (как shield 4.1.0) |
|---|---|---|---|
| новые TCP-соединения | 300/мин → бан 15 мин | 6 000/мин, без бана | **40 000/мин**, запас 60 000, без бана |
| SYN | 50/с → бан 15 мин | 200/с без бана; бан от 1 000/с | **2 000/с**, запас 3 000, без бана |
| UDP | 20 000/с → бан 15 мин | то же | 20 000/с, запас 40 000, **без бана** |
| одновременные соединения | 15 000 | 15 000 | 15 000 |

- Бан за SYN-флуд — только по желанию: `TCP_SYN_BAN_RATE=<SYN/с>` в `/etc/shieldnode/config.conf`
  (по умолчанию `0` — выключен).
- В пульте `guard` срезанное без бана видно отдельной строкой «Ограничение частоты (без бана)»,
  новый счётчик `c_drops_udp_limit_v4`.

## 1.4.2 — установщик 1.4.2, node 1.2.1, shieldnode 1.2.1 (2026-09-27)

**Обычные клиенты VPN больше не попадают в бан «Флуд соединениями».** Раньше IP банился на 15 минут
за первое же превышение 50 SYN/с (запас 100) или 300 новых соединений в минуту (запас 600). VLESS без
mux открывает к ноде отдельное TCP-соединение на каждое соединение приложения, а за мобильным CGNAT
на одном IP сидит много людей. На лабе один клиент, открывший 400 соединений разом (обычная загрузка
тяжёлой страницы), получал бан: 8 103 отброшенных пакета, 15 минут без новых соединений.

Теперь по защищаемым TCP-портам:
- **мягкий лимит без бана**: больше 200 SYN/с (запас 400) или 6 000 новых соединений в минуту
  (запас 3 000) с одного IP — лишнее отбрасывается, клиент повторит попытку, его остальные соединения
  и соседи по CGNAT не страдают;
- **бан только за явный SYN-флуд**: больше 1 000 SYN/с (запас 2 000) с одного IP, на 5 минут (было 15);
- в пульте `guard` отдельные строки: «Флуд соединениями TCP/SYN (бан)» и «Ограничение частоты
  подключений (без бана)»; новые счётчики `c_drops_syn_limit_v4`, `c_drops_newconn_limit_v4`.
- **Транзитный трафик больше не попадает под лимиты.** Цепочка prerouting видит и пакеты, которые идут
  *через* машину: исходящие соединения Docker-контейнеров в режиме bridge, гостей LXD/KVM. Контейнер,
  открывший много соединений на :443 (TCP или QUIC/UDP) в интернет, считался «флудером» по защищаемому
  порту. Лаба: хост с shieldnode забанил свою VM на 15 минут за 400 исходящих соединений. Теперь пакеты,
  адрес назначения которых не принадлежит ноде, пропускаются до лимитов; входящие к ноде (и к опубликованным
  портам Docker — DNAT на этом этапе ещё не сделан) проверяются как раньше.
- Свои значения в `/etc/shieldnode/config.conf` по-прежнему главнее: `TCP_SYN_RATE`, `TCP_NEW_RATE`,
  новые `TCP_SYN_BAN_RATE`/`TCP_SYN_BAN_BURST`, `TCP_ABUSERS_TIMEOUT`.

## 1.4.1 — установщик 1.4.1, node 1.2.1, shieldnode 1.2.0 (2026-09-26)

Исправления по отчёту с чистого сервера (Ubuntu 24.04, 6.8.0-111, 4 ГБ):
- **Ложный ✗ у `net.ipv4.tcp_mem` в «Статус оптимизации».** Значение считается от объёма RAM (MemTotal),
  а он после перезагрузки отличается на десятки КБ — план расходился с применённым значением на 1 страницу.
  Теперь `tcp_mem` округляется до целых мегабайт (одинаков между загрузками, повторный apply не переписывает
  файл), а статус допускает расхождение до 1% для этого ключа (показывает `✓≈`).
- **Отрицательные дельты в «perf since apply» после перезагрузки** (`squeeze=-0.392%`): счётчики ядра
  обнуляются при загрузке, прежняя проверка «счётчики меньше» это не ловила. Теперь сравнивается идентификатор
  загрузки: после reboot статус пишет «был reboot — дельты появятся после следующего apply».
- **«LIMIT: NIC дропает на приёме» из-за одного пакета.** Предупреждение — только если дропов ≥ 100 или
  больше 0,1% принятых пакетов.

## 1.4.0 — установщик 1.4.0, node 1.2.0, shieldnode 1.2.0 (2026-09-25)

Разбор причин и доказательства — `docs/DIAGNOSIS.md`.

### Порты и фаервол (shieldnode)
- **Инбаунды — из конфигурации Xray (API), а не из списка сокетов** (E1/E2). Раньше каждый исходящий UDP-поток
  клиента (DNS, QUIC) выглядел как «слушающий порт» и попадал в `protected_udp` (~70 мусорных портов на лабе,
  вечные WARN в проверке). Без API — осторожная эвристика (UDP-порт берётся, только если он стабилен и есть TCP-пара,
  он вне эфемерного диапазона или зарезервирован).
- **Защищаемые порты следят за реальностью** — служба `shieldnode-ports` (E3): инбаунды, UFW, SSH, API ноды;
  новый инбаунд из панели защищён в течение минуты (лаба: 17 с).
- **API ноды (2222) закрыт для всех, кроме `TRUSTED_IPS` и источников UFW** — панель остаётся подключённой.
- **Фаервол поднимается при загрузке до сети и Docker** (P0-2): `shieldnode.service` без DefaultDependencies,
  `Before=network-pre.target docker.service`. Лаба: 18.9 с (было 26.5–27.7 с — после поднятия NIC).
- **IPv6 fail-safe**: любой IPv6-пакет отбрасывается на входе и выходе, в том числе в аварийном режиме.
- `shieldnode verify` — проверка «фаервол жив» (хуки, число правил, fail-safe, наборы, IP SSH-сессии в белом
  списке); установщик завершает установку ошибкой, если verify не проходит (E8).

### Блок-листы и проверка
- Свой список больше не остаётся пустым после применения (E4): гард «тот же контент» пропускает только если
  набор в ядре непуст; то же для интервального гарда фидов.
- После перезагрузки и применения блок-листы сразу восстанавливаются из последнего снимка (раньше — пусто 2–5 мин).
- CrowdSec без решений — честный статус «ждём community-список», не сбой и не алерт; «застрявший» агент
  перезапускается не чаще раза в час, максимум 3 раза.
- Таймеры обновления (CrowdSec, фиды, очистка) больше не «умирают» после применения: раньше после `vpn-node apply`
  таймер CrowdSec не срабатывал до перезагрузки (на лабе — 3 ч без обновления).
- Журнал применения называет оба интервала (фиды — 6 ч, CrowdSec — 30 мин).
- **Пульт `guard` показывает ровно проблемы проверки `status` + `verify`** (E5: был «Проблем не найдено» при WARN=12).
- Проверка: SSH слушает, IP сессии в белом списке, заполнение conntrack, состояние IPv6 хоста.

### IPv6 (node)
- **IPv6 выключен всегда и надёжно** (E6): `ipv6.disable=1` в cmdline (grub.d), sysctl на каждом интерфейсе,
  drop-in systemd-networkd `LinkLocalAddressing=no`, Docker `"ipv6": false`. Не откатывается; переключатель в меню убран;
  `HARDEN_IPV6=0` игнорируется.

### Оптимизация (node)
- **XanMod не ставился нигде** (E7): ошибка `pipefail` в проверке «чужого источника» обрывала шаг. Исправлено;
  **XanMod теперь по желанию** (`ENABLE_XANMOD=0` по умолчанию, пункт меню с объяснением риска и перезагрузкой).
- Установка XanMod безопасна: отказ при UEFI Secure Boot (неподписанное ядро не загрузится — на лабе
  нода не поднялась), проверка места в /boot, **пробная первая загрузка** (по умолчанию остаётся штатное
  ядро, XanMod становится ядром по умолчанию только после успешной загрузки). Сравнение на лабе:
  выигрыша в скорости к пользователю XanMod не дал — остаётся по желанию.
- `netdev_budget_usecs` считается под все установленные ядра (раньше первая загрузка XanMod
  заканчивалась ошибкой systemd-sysctl).
- `ip_local_reserved_ports` резервирует реальные инбаунды из контракта shieldnode, а не случайные UDP-сокеты;
  обновляется вместе с портами (`node reserve-ports`).
- Настройка fq работала не на всех NIC: у multiqueue virtio дочерние fq под `mq 0:` неадресуемы — корневой mq
  пересоздаётся с `handle 1:`.
- fq реально ставится на сетевую карту сразу при применении (раньше — только после перезагрузки); откат
  возвращает дефолтный qdisc ядра; служба `node-fq-tune` больше не остаётся в состоянии failed после обновления.
- Drop-in `LimitNOFILE` ставится только юнитам с xray/remnanode в `ExecStart` (раньше попадал на юнит shieldnode).
